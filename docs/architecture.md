# warifuri の構成

この文書には、[原則](principles.md)から導いた warifuri の組み立てを書きます。2つの文書が食い違ったときは、原則のほうを正とし、この文書を直します。

## 言葉

| 言葉 | 意味 |
|---|---|
| 人、本人 | warifuri のサーバーを使う1人 |
| サーバーの機械 | warifuri のサーバーを動かしている機械 |
| 使う機械 | ハーネスで warifuri につないでいる機械。データベースでは「デバイス」と呼び、機械ごとに1つの名前を持つ |
| データベース | ゴール、タスク、順序、着手の記録、習慣、予定、作業フォルダ、秘書の自律度、変更の記録を入れた SQLite のファイル |
| 核 | データベース、MCP サーバー、HTTP API、プロフィールと設定の配布 |

## 全体の形

warifuri の核に、スケジュール、秘書、連絡手段などを、要るものだけプラグインとして足します。カレンダーはプラグインにせず、使う人のエージェントが自分のカレンダーの MCP で読み書きします(プラグインの節のカレンダー)。

使う機械が何台あっても、どのハーネスからでも、同じデータベースを同じ MCP サーバーで読み書きします。

```
  Mac の Claude Code ──────┐
  Mac の Codex ────────────┤
  ほかの PC のハーネス ─────┼─ MCP(GitHub でログイン) ─▶ ┌────── warifuri のサーバー ──────┐
                           │                             │ 核: データベース、MCP サーバー、│
  使う機械のフック ─────────┴─ HTTP(シークレット) ────▶ │     HTTP API、プロフィールと設定 │
                                                         │ ─────────────────────────────── │
                                                         │ プラグイン(入れたいものだけ)    │
                                                         │   スケジュール、秘書、          │
                                                         │   連絡手段、機械                │
                                                         └─────────────────────────────────┘
```

## 核1: データベース

### データベースが持つもの

| もの | 主な項目 | 原則 |
|---|---|---|
| ゴール | 題名、あるべき姿、期日(仮の印つきもある)、状態、だれの時間を使うか、人が主導か、プロフィール | 1, 2, 8, 20 |
| タスク | 題名、説明(`body`)、完了の条件、ゴール、状態、だれの時間を使うか(`mode`)、重さ(`load`)、見積り、期限(任意)、作業フォルダ、次の一手(`next`)、任せるの印 | 3, 4, 5, 6, 8 |
| 順序 | タスクどうしの「こちらが先」 | 3 |
| 着手 | どのタスクを、どのデバイスの、どの作業フォルダで、いつから作業しているか | 7 |
| 習慣 | 題名、繰り返しの決まり(毎週金 9:00〜10:30 など)、長さ、つながるゴール | 21 |
| 予定 | 題名、種類(タスク、習慣、固定)、つながるタスクか習慣、始まりと終わり(UTC で持つ)、メモ、出どころ(`source`)と外の予定の id(`external_id`) | 3, 21 |
| 作業フォルダ | 名前、属するプロフィール、デバイスごとのディレクトリ(同じ作業フォルダでも Mac と Windows でパスが違う) | 20 |
| 秘書の自律度 | 秘書の動きの種類ごとの自律度と、了承・取り消しの回数 | 13 |
| 報告 | 秘書が人に向けて書いたもの。種類(毎晩の見張り `nightly`、朝のまとめ `morning`、受信箱の整理 `inbox`)、題名、本文、書いたデバイス、書いた時刻 | 13 |
| 記録 | だれが、どのデバイスから、いつ、何を変えたか。プロフィールと設定の変更も入る | 9, 18 |

ゴールとタスクの状態は、`ready`、`running`、`waiting`、`deferred`、`done`、`discarded` の6つです。`waiting` は待ちで、本人の判断を待つときも、指導教員や先方の返事のように人の外を待つときも使います。

重さ(`load`)は「重い・普通・軽い」の3つで、任意です。人の時間を使うタスクで分かるときだけ入れ、空なら普通として扱います。スケジュールを組むとき、重い作業を集中できる時間に置くために使います。説明(`body`)は背景と範囲を書く欄で、目安は2,000字までです。長い仕様や手順はリポジトリの文書に置き、その場所を書きます。

優先度の数字は持ちません。どれを先にやるかは、ゴールの期日、順序、秘書の判断から出します。秘書がいなければ、人とエージェントがこれらから決めます。

習慣はゴールやタスクとは別の表です(原則21)。予定は、タスクか習慣に時間を割り当てたものか、ほかの人との約束のような固定の予定です。予定は重なってもかまわず、組み直すときは動かすか消します。消すのは予定だけで、タスクと習慣は残ります(原則3)。ナレッジはデータベースに入れず、プロフィールに置きます(原則21、22)。

予定の出どころ(`source`)と外の予定の id(`external_id`)は、その予定が外のカレンダーのどの予定にあたるかを表します。`source` には `google-calendar` のような短い名前を、`external_id` にはそのカレンダーでの予定の id を入れます。1つの組は1つの予定にだけ付き、`external_id` は `source` なしには入れられません。エージェントが自分のカレンダーの MCP で外の予定を読んで `book` で入れるとき、同じ組の予定がすでにあれば、新しく作らずにその予定を直します。同じ予定を何度取り込んでも、予定は1つのままです。

逆に、warifuri の予定を外のカレンダーに書き出したときは、返ってきた予定の id を、`book` で id を渡してその予定に付けます。カレンダーの MCP は外の予定に見えない印を残せないので、外の予定のうち warifuri が書いたものは、この組で見分けます。取り込むときは、組が warifuri にある予定を飛ばすか、それに合わせて直すかし、組のない外の予定を書き換えることはしません。

報告は足すだけで、直したり消したりはしません。題名は1行で200字まで、本文はふつうの文字か軽い Markdown で20,000字までです。書いたことは記録にも残ります(種類は `report`)。

習慣の繰り返しの決まり(`rule`)は、`{"days": ["月", "水", "金"], "window": "07:00-07:30"}` のような形で書き、データベースには JSON の文字列で持ちます。`days` はどの日に行うかで、`"daily"`(毎日)、`"weekdays"`(月〜金)、または月〜日の曜日の並びのどれかです。`window` は任意で、その日のどの時間帯に置くかを `HH:MM-HH:MM` で書きます。終わりが始まりより前なら日をまたぎ(`23:00-07:00` は始まりの日の分です)、習慣の長さ(`duration_min`)はこの時間帯に収まらなければなりません。`window` がなければ、その日のどこに置いてもかまいません。読めない決まりは断ります。曜日の並びは月〜日の順に直してから持つので、同じ決まりを別の順で渡しても変更になりません。時刻はサーバーの機械の時計で読みます(`schedule` と同じです)。

スケジュールを組むときは、習慣を期間の中の回に広げてから置きます。`src/ledger/habits.mjs` の `habitOccurrences` が、期間(`from` から `to` の手前まで)と時間帯が重なる回を、その日の日付と、時間帯の始まりと終わり(UTC)と、長さを付けて返します。止めた習慣には回がありません。

### 空き時間

`free_time` のツールは、期間(`from` から `to` の手前まで、`schedule` と同じ読み方)の中で、タスクを置ける空き時間を、上限(原則14、下の「生活、場所、上限」の小節)の中で返します。中身は `src/ledger/freetime.mjs` の `freeTime` で、データベースも時計も読まない関数です。一度に聞ける期間は31日までで、それより長ければ断ります。

日はサーバーの機械の時計で区切り、期間と重なる日ごとに1つ返します。その日に置いてよいのは、上限の `earliest` から `latest` までを、期間で切った部分です。予定は、種類によらずどれも埋まった時間として扱います。

習慣は先に置きます。その日の回のうち、時間帯の中にその習慣の予定がまだない回を、時間帯の中で、埋まった時間に重ならずに長さが収まるいちばん早いところに置きます。時間帯のない習慣は、`earliest` から `latest` のあいだに置きます。置く順は、時間帯のある習慣が先で(置ける幅が狭いため)、そのあとは時間帯の始まりの順です。置いた回は埋まった時間になり、呼び出す側が `book` で入れられるように `habits_to_place` に並べます。どこにも収まらない回は、`starts_at` を null にして並べます。

1日の上限(`day_max_hours`)に数えるのは、タスクと習慣の予定と、いま置いた習慣のうち、その日の `earliest` から `latest` に入っている時間です。期間で切る前の、その日全体で数えます。固定の予定は埋まった時間にはなりますが、上限には数えません。寝る時間や朝の運動のように、`earliest` から `latest` の外にある時間も数えません。残りの時間を `remaining_hours` として返します。

残った時間を空きに分け、`block_min_minutes` より短い空きは外します。空きは早いものから並べ、足して `remaining_hours` を超えるところで、その空きを短くします。短くして `block_min_minutes` に届かなければ、その空きから先は出しません。そのため、1日に出す空きは、上限の残りを超えません。`block_max_minutes` より長い空きはそのまま返すので、予定を入れる側が、その長さまでに切って入れます。

返す形は次のとおりです。時刻は UTC の ISO 日時、`date` はサーバーの機械の時計での日付です。例は、日本時間の機械で、12時から13時にタスクの予定が1つあり、9時から10時のあいだに30分の散歩の習慣がある日です。

```json
{
  "from": "2026-11-01T15:00:00.000Z",
  "to": "2026-11-02T15:00:00.000Z",
  "limits": { "day_max_hours": 8, "block_min_minutes": 30, "block_max_minutes": 120, "earliest": "09:00", "latest": "21:00" },
  "days": [
    {
      "date": "2026-11-02",
      "booked_hours": 1,
      "remaining_hours": 6.5,
      "habits_to_place": [
        { "habit_id": "h_…", "title": "散歩", "duration_min": 30, "window_start": "2026-11-02T00:00:00.000Z", "window_end": "2026-11-02T01:00:00.000Z", "starts_at": "2026-11-02T00:00:00.000Z", "ends_at": "2026-11-02T00:30:00.000Z" }
      ],
      "free": [
        { "starts_at": "2026-11-02T00:30:00.000Z", "ends_at": "2026-11-02T03:00:00.000Z", "minutes": 150 },
        { "starts_at": "2026-11-02T04:00:00.000Z", "ends_at": "2026-11-02T08:00:00.000Z", "minutes": 240 }
      ]
    }
  ]
}
```

決まりが読めない習慣(取り込みで確かめ待ちになったもの)は置かずに、その id を `skipped_habits` に並べます。

### 着手

エージェントは、作業を始めるときに `start` でタスクに着手します。

- 1つのタスクに着手できるのは1か所です。別のデバイスや作業フォルダで `start` すると作業する場所が移り、そのことが記録に残ります。
- 同じデバイスの同じ作業フォルダで着手できるのは1件です。すでに1件作業中のところで別のタスクを `start` すると断り、いま作業中の1件を返します。先に手放してから始めます。作業フォルダで作業中のこの1件が、その作業フォルダの「いまの1件」で、着手ゲート(下の HTTP API)はこれを見ます。
- 同じ機械で Claude Code と Codex を使っても、デバイスは1つです。どちらから `start` しても同じ「いまの1件」を見ます。
- 閉じる、待ちにする、先送りにする、中断する(`release`)のどれかで手放します。手放すときは、次に着手する人のために `next` を1行書きます。
- `board` とフローチャートには「mac で作業中」のように出ます。
- 前のタスク(順序)がまだ閉じていなくても着手できます。順序は計画なので、`start` は止めずに、閉じていない前のタスクを返して知らせます(原則3)。

### 決まりはデータベースが守る

決まりは、AI が覚えていることに頼らず、データベースが書き込みを受けつけるかどうかで守ります(原則11)。決まりに合わない書き込みは、何も書かずに断り、足りないものを返します。

人の時間を使うゴールは、あるべき姿と期日がないと作れません。仮の印の付いた日付は期日として受けつけません(原則1、2)。人の時間を使うタスクを持つゴールは、人の時間を使うゴールとして扱います。人の時間を使うタスクは、完了の条件がないと作れません(原則5)。待ちにするにはだれの何を待つか、完了には成果、破棄には理由、先送りにはいつ見直すかが要ります(原則5、6)。

変更はすべて、だれとして、どのデバイスから書かれたかを記録に残します。ただし、同じデバイスの人と AI は、データベースからは見分けられません。期日を人が決めたかどうかは書き手の申告によります(原則2)。

warifuri は、データベースの中で見せる範囲を区切りません。ログインした本人には全部が見えます。

### 外から取り込む

ほかのツールからの引っ越しや写しのために、データベースはスナップショットの JSON を受け取れます([スナップショット](snapshot.md))。取り込みは、「決まりに合わない書き込みは断る」という決まりの唯一の例外です。決まりに合わない行も、要確認の印(`review`)を付けて入れます。印の付いた行は、次に書き換えるときに決まりを満たさなければ書けません。満たせば印は消えます。

## 核2: MCP サーバー

### ツール

| ツール | やること | 主に使う人 |
|---|---|---|
| `board` | 開いているゴールと、その下のタスクを一覧する。ゴールごとに、次に着手できるタスク(着手可能)を先に並べる。作業フォルダを渡すと、既定でその作業フォルダのプロフィールの分だけ返す。全部を見たいときは明示する | みんな |
| `get` | ゴールかタスクを1件、順序と記録と説明つきで読む | みんな |
| `places` | 作業フォルダを、プロフィールとデバイスごとのパスつきで一覧する。タスクがまだない作業フォルダも出る | エージェント、秘書 |
| `search` | 題名で探す。作る前に、同じものがないかを見る。閉じたものも探せる | エージェント |
| `flow` | ゴールごとのフローチャートを Mermaid で返す。順序の矢印と、状態(完了、作業中、着手可能、待ち)の色 | みんな |
| `stale` | 片づけの候補を出す。作業中のまま動きがない、`ready` のまま長く触られていない、待ちのまま動きがない、など。日数はプロフィールの既定値で変えられる。閉じはしない | 秘書、人 |
| `create_goal` / `create_task` | ゴールやタスクを作る。タスクはゴールなしでも作れる。ゴールの下に作るタスクには、前のタスク(`after`)を一緒に渡して順序をつなぐ | エージェント、秘書 |
| `update` | 題名、説明、完了の条件、期限、`mode`、重さ、ゴールの付け替え、人が主導の印と任せるの印を直す | みんな |
| `link` / `unlink` | タスクどうしの順序を足す、外す | みんな |
| `start` / `release` | タスクに着手する、手放す(手放すときは `next` を書く) | エージェント |
| `close` | 完了か破棄にする。成果か理由を付ける。分かったことがあれば一緒に渡す | エージェント、秘書 |
| `reopen` | 完了や破棄から `ready` に戻す | 人、秘書 |
| `resume` | 先送りや待ちから `ready` に戻す | エージェント、秘書 |
| `defer` | 先送りにする。いつ見直すかを付ける | エージェント、秘書 |
| `wait` | 待ちにして、だれの何を待つかを書く | エージェント |
| `habit` | 習慣を作る、直す、止める。id を渡さないと作り、題名と繰り返しの決まり(`rule`)と長さ(`duration_min`)が要る。id を渡すと、渡した項目だけを直す。`stop` で止める(消さずに、記録と一緒に残る)。止めた習慣は `active` で戻せる | 秘書、人 |
| `book` | 予定を入れる。id を渡すと、その予定を直す。タスクか習慣の予定は、題名を省くとそのタスクか習慣の題名になる。固定の予定には題名が要る。始まりと終わりは時差つきの ISO 日時で、長さは24時間まで。重なりは断らず、重なる予定を一緒に返す。`source` と `external_id` で外の予定を名指しでき、id を渡さずに同じ組の予定がすでにあれば、その予定を直す。id を渡して組を付けるとき、ほかの予定がその組を持っていれば断る。`external_id` だけでは断る | 秘書、エージェント |
| `unbook` | 予定を消す。消した予定は記録に残る | 秘書、エージェント |
| `schedule` | 期間(`from` から `to` の手前まで)に重なる予定を、始まりの順に一覧する。日付だけならサーバーの機械の時刻で0時、省くと今日。予定ごとに、タスクの題名と状態、ゴール、プロフィール(タスクのゴールの、なければタスクの作業フォルダの)、出どころと外の予定の id を付ける | みんな |
| `free_time` | 期間(`from` から `to` の手前まで、31日まで)の、タスクを置ける空き時間を日ごとに返す。上限の時刻の中で、予定を避け、まだ入っていない習慣を先に置いて(`habits_to_place`)、`block_min_minutes` より短い空きを外す。1日の空きは `day_max_hours` の残りを超えない(上の「空き時間」の節) | 秘書、エージェント |
| `place` | 作業フォルダを登録する、直す(プロフィール、デバイスごとのパス) | エージェント、秘書 |
| `context` | 作業フォルダ(id か作業しているディレクトリ)かプロフィールを渡すと、そのプロフィールの people.md と knowledge.md と受信箱の inbox.md、`knowledge/` と `procedures/` の中のファイル名の一覧を返す。手順や分けたナレッジの本文は、`name` に名前を渡して取りにいく | エージェント |
| `note` | ナレッジに書き足す。`kind` が `human`(人の言葉)なら「本人の言葉」としてすぐに knowledge.md へ、`agent`(エージェントの気づき)なら受信箱の inbox.md へ(秘書がいなければ「未確認」として knowledge.md へ) | エージェント、秘書 |
| `profile`(予定) | プロフィールの既定値を読む、書く | 秘書、人 |
| `settings` | 使う人の設定(生活、場所と移動時間、上限)を読む、書く。何も渡さなければ読むだけで、書いていない項目は既定値で返す。上限は、本人が決めたことを `by_person: true` で示したときだけ書ける(下の「使う人が書く設定」の節) | 秘書、エージェント、人 |
| `autonomy` | 秘書の自律度の一覧を読む。動きの種類ごとに、自律度、続いた了承の回数、取り消しの回数、人の明示で決めたかを返す | みんな |
| `autonomy_outcome` | 秘書の案に人がどう答えたか(そのまま了承、直して了承、断った、あとから取り消した)を1件書く。了承が続けば自律度を上げ、取り消しで戻し、変わったかを返す | 秘書 |
| `autonomy_set` | 人の明示で、動きの種類の自律度を直接決める | 秘書、人 |
| `report` | 報告を1件書く。種類(`nightly`、`morning`、`inbox`)、1行の題名、本文を渡し、書いた報告を返す。書いたデバイスは呼び出したデバイスになる | 秘書 |
| `reports` | 報告を新しい順に読む。種類で絞れる。`limit` は既定で10件、50件まで。`before` に報告の id か時差つきの ISO 日時を渡すと、それより古いものだけを返す。続きがあれば、次に `before` に渡す id(`next_before`)を返す | みんな |

(予定)と付けたツールは、v0.1 にはまだありません。

書くツールは、呼び出したデバイスとして書きます。デバイスはシークレットか GitHub のログインのトークンから決まり、ツールの引数では渡せません。記録の「だれとして」には、どう入ったかが入ります。シークレットなら `device-key`、GitHub のログインならアプリの `oauth:<client_id>` です。決まりに合わず断った書き込みは、ツールのエラーとして、足りないものを日本語で並べて返します。

デバイスは、最後にシークレットかトークンで warifuri サーバーを呼んだ時刻(`last_seen_at`)を持ちます。呼び出しのたびに書かないよう、1つのデバイスにつき1分に1回までしか更新せず、記録にも残しません。`warifuri key list` に出ます。

`start` の作業フォルダは、作業フォルダの id か、作業しているディレクトリで渡します。ディレクトリなら、そのデバイスでそこを含む一番深い作業フォルダを使います。どの作業フォルダにも入らないディレクトリでは断り、`place` で登録するよう返します。`release` では `next` を1行書くことが要ります。

`close` で渡した「分かったこと」(`learned`)は、閉じたときの記録に残したうえで、`note` の `agent` と同じ道で、ゴールかタスクのプロフィールに入れます。プロフィールが分からないときは、記録に残すだけにして、そのことを返します。

秘書の自律度(原則13)の動きの種類は、コードに決めた一覧です。ずれた予定の組み直し(`reschedule_block`)、受信箱の整理(`tidy_inbox`)、予定をカレンダーに書き出す(`write_calendar`)が段階2、閉じ忘れたタスクを閉じる(`close_forgotten`)、タスクをほかのゴールへ移す(`move_task`)、ゴールにつながっていないタスクを束ねる(`bundle_loose_tasks`)、ナレッジに入れる(`add_knowledge`)、分ける(`split_knowledge`)、古い印を付ける(`mark_stale_knowledge`)が段階3です。段階4の動きは一覧になく、どのツールでも任せられません。一覧にない種類は断ります。

どの種類も「聞いてから」(`ask`)で始まります。秘書は案を出して答えをもらうたびに `autonomy_outcome` を呼びます。そのまま了承(`approved`)が3回続くと「やってから知らせる」(`act_then_tell`)に上がります。直して了承(`changed`)か断った(`refused`)なら、続いた回数は0に戻ります。あとから取り消した(`revoked`)なら、回数を0に戻し、「やってから知らせる」だった種類は「聞いてから」に戻します。自律度が変わったときは `level_changed` と、人に一度だけ伝える一言(`announce`)を返します。`about` にゴールかタスクを渡すと、人が主導するゴール(原則8)での了承は回数に数えません。3回という数は、人が warifuri を入れたときに了承した既定値です。

`autonomy_set` は、人が「これは聞かなくていい」「これは毎回聞いて」と言ったときだけ使います。人の明示であることを `by_person: true` で示し、付けなければ断ります。本人の言葉は `said` に渡すと記録に残ります。人の明示で「聞いてから」にした種類は、了承が続いても上げません。どの書き込みも、`entity` が `autonomy` の記録に、結果や人の明示かどうかと一緒に残ります。

プラグインも、自分のツールを MCP サーバーに足せます。予定を入れる `book`、消す `unbook`、読む `schedule` と、人の空き時間を聞く `free_time` は核にあります。スケジュールのプラグインは、これらを使って予定を組みます。

### HTTP API

作業の前に、この作業フォルダで作業中のタスクがあるかを確かめるフックのように、AI ではなくスクリプトが warifuri サーバーに聞く場面があります。こうした場面のために、HTTP API を出します。スクリプトは、人のログインではなく、シークレット(`warifuri key add <デバイスの名前>`)で warifuri サーバーに聞きます。シークレットはデバイスに結びつくので、フックは自分のデバイスの「いまの1件」を見ます。

いまの HTTP API は、着手ゲートに使う `GET /api/held?dir=<絶対パス>` の1つです。`Authorization: Bearer wf_…` にシークレットを付けて聞くと、そのディレクトリが入る作業フォルダと、そこでこのデバイスが作業中のタスクを返します。どちらもなければ null です。どの作業フォルダにも入らないディレクトリでは、作業フォルダの外で作業中のタスクを返します。GitHub のログインのトークンは、MCP サーバーのために出したものなので、ここでは受けつけません。呼び出しの回数は、呼び出し元のアドレスごとに1分に600回までです。

### つなぎ方

使う機械は、ハーネスに URL を登録すれば使えます。初回にブラウザが開くので、GitHub でログインし、許可の画面でこの機械のデバイスの名前を選びます(新しく付けるか、同じ機械の別のハーネスで付けた名前を選ぶ)。

```bash
claude mcp add --transport http warifuri https://<サーバー>/mcp
```

ハーネスごとの登録の仕方の違いは、`warifuri connect` が吸収します。`connect` とフックを使うときだけ、使う機械にも warifuri を入れます。

```bash
warifuri connect --url https://<サーバー> --device <デバイスの名前>
```

`connect` は、PATH にある `claude` と `codex` を見つけ、それぞれに MCP サーバーを `warifuri` の名前で登録します(Claude Code は `claude mcp add --scope user --transport http`、Codex は `codex mcp add --url`)。`--harness` で片方だけにもできます。サーバーの URL はデータのフォルダの `warifuri.env` に `WARIFURI_SERVER_URL` として書き、フックはそこから読みます。`--url` を省くと、この機械のサーバー(`http://127.0.0.1:<ポート>`、GitHub のログインがあればその公開の URL)を使います。

サーバーのデータベースが同じ機械にあるときは、`connect` がデータベースを直接開いて、このデバイスのシークレットを発行し、`WARIFURI_DEVICE_KEY_FILE`(既定はデータのフォルダの `device.key`)に本人だけが読める形で置きます。シークレットのファイルがあり、そのシークレットがまだ使えるなら、新しくは発行しません。この場合に GitHub のログインを設定していなければ、ハーネスはシークレットで warifuri サーバーに入ります。Claude Code には `Authorization` のヘッダーとして登録し、Codex には `WARIFURI_DEVICE_KEY` の環境変数から読むように登録します。Codex を使う人は、Codex を起動する環境で、この変数にシークレットのファイルの中身を入れておきます。サーバーが別の機械にあるときは、ハーネスには URL だけを登録し、最初の利用のときに GitHub でログインします。着手ゲートに使うシークレットは、サーバーの機械で `warifuri key add <デバイスの名前>` を実行して、出たシークレットをシークレットのファイルに1行で書きます。`connect` はその手順を表示します。シークレットは画面にもログにも出しません。

あわせて、着手ゲートのフック(下の節)を Claude Code の `~/.claude/settings.json` と Codex の `~/.codex/hooks.json` に足し、パッケージの `harness/skills/` にある指示書を、それぞれの skills のフォルダに写します。ほかのフックや設定はそのまま残し、ファイルを書き換える前に、元のファイルを `<ファイル>.bak-warifuri-<日時>` として隣に写します。すでに入っているものは書き換えないので、何度実行しても同じ形になります。指示書は、すでにあるファイルを残し、`--force` のときだけ上書きします。`--no-hook` と `--no-skills` でそれぞれを省けて、`--dry-run` では何も変えずに、することだけを出します。Windows では、ホームを `%USERPROFILE%` から読み、`warifuri.cmd` もコマンドとして探します。

### 着手ゲート

着手ゲートは、ファイルを編集するツール(Claude Code の Edit、Write、MultiEdit、NotebookEdit と、Codex の apply_patch)の前に走る PreToolUse のフックで、`warifuri hook gate` が中身です。ハーネスが渡す JSON を標準入力で受け、編集するファイルのディレクトリ(まだないディレクトリなら、一番近い親)を `GET /api/held` で聞きます。そのデバイスで作業中のタスクがあれば通し、どの作業フォルダにも入らないディレクトリでも通します。作業フォルダに入るのに作業中のタスクがないときだけ止め、`search` で同じタスクを探し、なければ `create_task` で作り、`start` に `place` としてそのディレクトリを渡して着手するよう、エージェントに返します。Claude Code と Codex は同じ形の JSON を受け取るので、1つのコマンドで両方に使えます。Codex では、足したフックを `/hooks` で一度信頼すると動きます。

フックは、止めるべきか分からないときは止めません。URL やシークレットがない、warifuri サーバーが3秒で答えない、200 以外を返す、受け取った JSON が読めない、のどれでも通します。`WARIFURI_GATE=off` にすると、いつでも通します。

ログインしてよい人は、設定に GitHub のユーザー名で1人だけ書きます。そこにない人は、ログインできても断ります。ただし、GitHub のユーザー名は手放されると別の人が取れるので、本人かどうかは名前ではなく GitHub の数値の ID で比べます。`WARIFURI_GITHUB_ID` に ID を書けばそれを使い、書かなければ、名前が合った最初のログインの ID をデータベースに覚えて、それからは ID だけを比べます。覚えた ID は `warifuri oauth clients` の最初の行に出ます。warifuri は、自分で OAuth の口になり、本人の確認だけを GitHub に任せます。GitHub のトークンを、そのまま warifuri サーバーに入るために使うことはしません。

GitHub でのログインには、GitHub の OAuth App を1つ作ります。GitHub の Settings の Developer settings にある OAuth Apps で新しく登録し、Authorization callback URL に `<公開の URL>/oauth/github/callback` を書きます。公開の URL は、ハーネスから見えるサーバーの URL です。`https://` で始まり、道を含まない形にします(手元で試すときだけ `http://localhost` も使えます)。サーバーには、公開の URL を `WARIFURI_PUBLIC_URL` で、ログインしてよい人の GitHub のユーザー名を `WARIFURI_GITHUB_USER` で、OAuth App の Client ID と Client Secret を `WARIFURI_GITHUB_CLIENT_ID` と `WARIFURI_GITHUB_CLIENT_SECRET` で渡します。Client Secret は秘密なので `secrets.env` に書くか、`WARIFURI_GITHUB_CLIENT_SECRET_FILE` でファイルの場所を渡します。前の2つは `warifuri serve` の `--public-url` と `--github-user` でも渡せて、そのときは引数のほうを使います。書く場所と読む順は[設定](configuration.md)にまとめました。どれか1つでも欠けると、ログインは使えず、シークレットだけで動きます。起動したときに、そのことを表示します。`warifuri config` でも、ログインが使えるかと、足りない項目を確かめられます。

GitHub には、ログインの名前と ID を読む以外の権限を求めません。読んだら、GitHub のトークンは捨てます。ハーネスが受け取るのは warifuri が出すトークンです。1時間で切れ、30日もつ更新用のトークンで取り直します。更新を続けても、最初にログインしてから90日たつと切れるので、そのときはログインし直します。どちらも許可の画面で選んだデバイスに結びつき、MCP サーバーでは、シークレットと同じように、どのデバイスからの呼び出しかを表します。つないだアプリの一覧は `warifuri oauth clients` で見られ、あるアプリのトークンをすべて取り消すには `warifuri oauth revoke <client_id>` を使います。機械をなくしたときは `warifuri key revoke <デバイスの名前>` を使います。そのシークレットと、そのデバイスで GitHub からつないだログインが、まとめて切れます。取り消したデバイスの名前は、許可の画面で選べず、新しい名前としても使えません。

ログインのあとにブラウザを戻す先は、アプリが登録のときに名乗ります。warifuri が受けつけるのは、その機械の中(`localhost`、`127.0.0.1`、`[::1]`)か、`https` の決まった先だけです。決まった先は `claude.ai` と `claude.com` で、`WARIFURI_REDIRECT_HOSTS` にカンマ区切りで足せます。許可の画面には、アプリの名前と並べて戻り先を出します。アプリの名前はアプリが自分で名乗ったものなので、戻り先のほうで確かめてください。

### 届かないとき

warifuri サーバーに届かないときも、作業は止めません。着手ゲートのフックは、warifuri サーバーに届かなければ通します。エージェントは、届くようになったら、届かなかったあいだの作業を登録して閉じます(指示書のひな形にそう書く)。登録し忘れたものは、あとで人が `stale` や一覧を見て拾います。

### Web 画面

warifuri サーバーは、台帳をブラウザで読むための画面も出します。カレンダー(`/calendar`)、タスク(`/tasks`)、サーバー(`/server`)、秘書(`/secretary`)、設定(`/settings`)の5つで、`/` はカレンダーに移ります。画面のファイルはパッケージの `src/web/` にあり、組み立ての手順は要りません。

| 画面 | 見せるもの |
|---|---|
| カレンダー | 1日か1週間の予定(`schedule` と同じもの)。重なる予定は横に並べ、8時から22時の外にある予定があれば、その分だけ時間を広げる。今日の予定の一覧と、色の見方 |
| タスク | 開いているゴールと、その下のタスク、ゴールのないタスク。ゴールごとに、順序から組んだフローチャートと、あるべき姿を出す。前のタスクが開いている `ready` は「順番待ち」と出す。期限切れ、3日以内、着手可能で絞れる |
| サーバー | 版、動いている時間、MCP サーバーの URL、データのフォルダの `backups/` にある最新の写しの時刻。取り消していないデバイスごとに、最後につないだ時刻と、作業フォルダごとに作業中のタスク |
| 秘書 | 秘書の報告を新しい順に30件まで。種類(毎晩、朝、受信箱)、題名、書いた日時、本文。本文は文字のまま出し、改行だけを残す |
| 設定 | プロフィール(名前、色、自己紹介)、作業フォルダ、デバイスとシークレットの状態、GitHub のログインでつないだアプリ |

画面が読むのは `/web/api/` の下の JSON で、30秒ごとに読み直します。書けるのは本人のプロフィールだけで、`POST /web/api/profile` に名前(40字まで)、自己紹介(400字まで)、6つから選ぶ色を JSON で送ります。値はデータベースの `settings` に `profile.name` のような名前で入り、変えたことは記録に残ります(種類は `settings`)。この書き込みは、`Content-Type: application/json` で、同じオリジンから来たもの(`Origin` が合うもの)だけを受けつけます。

だれが見られるかは、サーバーの置き方で決まります。

- この機械の中だけで待ち受けていて(`WARIFURI_HOST` が `127.0.0.1` などで)、公開の URL も、信じるプロキシも設定していないときは、この機械からのブラウザはログインなしで見られます。ほかのサイトが名前を付け替えてこの機械に向ける手口を防ぐため、`Host` が `localhost`、`127.0.0.1`、`[::1]` でない呼び出しと、転送のヘッダーが付いた呼び出しは断ります。
- それ以外のときは、ログインが要ります。`warifuri serve` は、起動したときにログインの URL を1つ表示します。この URL は1回だけ、15分まで使えます。URL のトークンは `#` の後ろにあり、ブラウザの外には出ないので、プロキシやサーバーのログに残りません。開くと、ページがトークンをサーバーに送り、アドレス欄と履歴からも消します。そして、HttpOnly、SameSite=Strict(https なら Secure も付けた `__Host-` の名前)のクッキーが入り、30日のあいだ見られます。ログインは、ハッシュにしてデータのフォルダの `web-sessions.json` に置くので、サーバーを動かし直しても切れません。GitHub のログインを設定しているときは、ログインの画面に「GitHub でログイン」も出ます。入れるのは、MCP サーバーと同じ、設定された1人だけです。

シークレットと GitHub のログインのトークンは、Web 画面では受けつけません。どの応答にも、シークレット、トークン、それらのハッシュは入れません。呼び出しの回数は、HTTP API と同じく、呼び出し元のアドレスごとに1分に600回までです。

プロフィールの色の点は、プロフィールのフォルダの `profile.yaml` に `color: "#rrggbb"` と書けばその色になります。書かなければ、よく使う名前にはあらかじめ決めた色、ほかは灰色を使います。

## 置き方と入れ方

### 置き方

| 使い方 | おすすめの置き場 | 口 |
|---|---|---|
| 試す | 自分の PC | `localhost` |
| 本気で使う | VPS か、家の使っていない PC | VPS は HTTPS で直接受ける。家の PC は Tailscale(中だけ、または Funnel で外から) |

本気で使うときは、つけたままにできる機械に置きます。秘書の毎晩の仕事は、その時間にサーバーが動いていないと走らないためです。独自ドメインは要りません。外に出す置き方では、warifuri のログイン、シークレット、プラグインが開ける口が、守りのすべてになります。

Tailscale の Funnel や Cloudflare Tunnel のように、同じ機械のトンネルを通して外から受けるときは、`warifuri serve` に `--trust-proxy loopback`(または `WARIFURI_TRUST_PROXY`)を付けます。付けないと、どの呼び出しもトンネルから来たように見えて、ログインの口の回数の制限を、知らない人とも分け合うことになります。トークンの口は、どのアプリからの呼び出しかで回数を数えるので、知らない人が叩いても、自分のアプリの更新は止まりません。

warifuri サーバーが受ける口は、MCP、HTTP API、Web 画面です。自分の口を持つプラグインは、何の口をどこに開けるかを、そのプラグインの説明に書きます。

### 入れ方

```bash
npm install -g warifuri
```

| コマンド | すること |
|---|---|
| `warifuri init` | データのフォルダを作り、設定ファイル `warifuri.env` のひな形と空の `secrets.env`、空の `profiles/` を置く。あるファイルは書き換えない。GitHub のログインの設定、最初のプロフィール、秘書を入れるか、常駐の登録(Linux は systemd、Mac は launchd、Windows はタスク スケジューラ)を対話で聞くのは予定 |
| `warifuri config` | すべての設定の値と、それをどこから読んだかを出す。秘密は伏せる |
| `warifuri serve` | サーバーを動かす |
| `warifuri connect` | 使う機械で、ハーネスに登録し、シークレット、着手ゲートのフック、指示書を入れる |
| `warifuri key add` | シークレットを発行する |
| `warifuri oauth clients` / `warifuri oauth revoke` | GitHub でログインしてつないだアプリを一覧する、そのトークンを取り消す |
| `warifuri backup` | データベースを日付つきのファイルに写す。新しいほうから `--keep` の数(既定は7)だけ残し、古いものは消す |
| `warifuri pack` / `warifuri init --from`(予定) | 別の機械に引っ越す |

### データのまとめ方と引っ越し

データベース、プロフィール、設定、秘密は、サーバーの機械の1つのフォルダ(既定は `~/.warifuri/`)にまとめます。ほかの機械には写しを持ちません。サーバーの機械に固有の値(URL、ポート、データの場所、GitHub のログインの設定、ログインしてよい人、時間帯、報告の時刻、秘書のハーネス、プラグインの設定)は、1つの設定ファイル `warifuri.env` に集め、コードには書きません。秘密だけは、同じフォルダの `secrets.env` に分けます。項目の一覧と読む順は[設定](configuration.md)に書きました。warifuri は git を使いません。変更の履歴はデータベースの記録と毎日の写しで持ちます。フォルダを自分で git にしたい人は、そうしてもかまいません。

引っ越しは3段にする予定です。`warifuri pack` と `init --from` は v0.1 にはまだないので、いまはデータのフォルダを写して運びます。

1. 古い機械で `warifuri pack`。データベースを安全に写し、フォルダを1つのファイルにまとめる。秘密を入れるかは聞く。
2. 新しい機械で `warifuri init --from <ファイル>`。設定ファイルを上から1項目ずつ「このままか、変えるか」確かめ、足りない秘密と常駐の登録を聞く。最後に、GitHub の OAuth App の戻り先を新しい URL に直すよう示す。
3. 使う各機械で、ハーネスの登録を新しい URL に付け替える(`warifuri connect --url <新しい URL>` か、ハーネスでの登録のし直し)。

秘書が使うハーネスのログインは、運ばずに新しい機械でし直します。

## プラグイン

この節に書くプラグインのうち、いま動くのは秘書の定時の仕事(下の「秘書のプラグイン」)だけです。Discord、機械の VM、`plugins.yaml` からのプラグインの読み込み、秘書の会話の常駐は、未実装の設計です。

### 用意するプラグイン

プラグインを1つも入れなくても、核はデータベースとして動きます。

| プラグイン | やること | 要るもの |
|---|---|---|
| スケジュール | 人の空き時間を探して予定を置く。習慣を先に置き、上限を守る | 個人の事実(生活、場所と移動、上限) |
| 秘書 | ゴールが期日に間に合うかを毎晩見て、自律度に従って組み直しや閉じ忘れの処理をする。受信箱を週に1回整理する | サーバーの機械で動くハーネスと、使う人が用意した資格情報 |
| 連絡手段: Web 画面 | スケジュール、データベース、フローチャート、秘書の自律度を見て、秘書と話す。人の時間を使うゴールの期日を確かめる | なし(warifuri のログインを使う) |
| 連絡手段: Discord | 秘書と話し、報告を受け取る | Discord のボット |
| 機械: 監視 | サーバーの様子を答える | Prometheus など |
| 機械: 作業用ブラウザ | 調べものを代わりに見に行く | ブラウザを動かす VM か PC |
| 機械: 実装用の手 | コードの直しを、隔離した機械で書いてテストする | 専用の VM |

秘書を入れるときの最小の形は、核にスケジュール、秘書、Web 画面を足したものです。外のサービスで必ず要るのは、GitHub のログインの設定だけです。Discord は、あとから足せます。秘書を入れず、エージェントが `free_time` と `book` を呼ぶだけの使い方もできます。

作業用ブラウザと実装用の手は、立てる手間も危うさも大きいので、warifuri には入れません。個人のプラグインとして書く例を示すだけにします。ほかは warifuri のプラグインとして用意します。

### カレンダー

warifuri は Google カレンダーに自分ではつながず、Google の資格情報も持ちません。カレンダーを読み書きするのは、使う人それぞれのエージェント(使う機械のハーネスや、サーバーの機械で動く秘書)です。エージェントは自分のカレンダーの MCP で予定を読み書きし、warifuri には核のツールで頼みます。そのためカレンダーはプラグインにせず、核の `book` と `schedule` だけで、プラグインを待たずに使えます。

主な使い方は読むほうです。エージェントは本人の予定を読み、`book` で固定の予定(`kind: "fixed"`)として入れます。`source` には `google-calendar` を、`external_id` にはその予定の id を渡します。同じ組で入れ直すと、新しく作らずにその予定を直すので(核1の予定の出どころ)、同じ週を何度取り込んでも予定は増えません。

書くほうでは、タスクと習慣に取った予定を、本人のふだんのカレンダーに書きます。warifuri 専用のカレンダーは作りません。エージェントは予定を作ったらすぐに、返ってきた予定の id を、`book` に warifuri の予定の id と `source`、`external_id` を渡してその予定に付けます。予定の説明に `warifuri:<予定の id>` のような行を書いて人に分かるようにしてもかまいませんが、見分けるのには使いません。カレンダーの MCP は予定に見えない印を残せないので、warifuri が書いた予定かどうかは、warifuri の側にある組だけで決めます。

取り込むときは、組がタスクか習慣の予定にある外の予定から、新しい固定の予定を作りません。本人がその予定をカレンダーで動かしていたら、warifuri の予定をそれに合わせて動かします。本人が直したほうを優先します。組のない外の予定は本人のものなので、書き換えも消しもしません。

どちらを正とするかは、予定の種類で分けます。固定の予定は Google のカレンダーが正で、warifuri はその写しを持ちます。タスクと習慣に取った時間は warifuri が正で、カレンダーにあるのはその写しです。ただし、上のとおり、本人がカレンダーで動かした分は warifuri に写します。

カレンダーに書くことは、組のある予定だけに触れるかぎり、秘書の段階2(自分の場所に書く)の動きで、種類は予定をカレンダーに書き出す(`write_calendar`)です。初めは毎回聞き、3回続けてそのまま了承されたら、やってから知らせるようになります(原則13)。本人の予定を書き換えたり消したりするのは段階4にあたるので、しません。軽い秘書は自律度を持たないので、書き出すたびに聞きます。

### 秘書のプラグイン

秘書は、サーバーの機械で、ハーネスのセッションとして動きます。頭に使うのは、改変していない Claude Code の `claude -p`(人のいないところで1回だけ動く形)です。Claude Code へのログインは、使う人がサーバーの機械で自分で行い、warifuri はその資格情報を読みも運びもしません。ほかのハーネスを秘書の頭に使うときは、各社の規約に合わせて API キーで使います。いま動くのは定時の仕事で、会話の常駐(Web 画面や Discord からの話しかけに答える)はまだありません。

#### 入れ方

サーバーの機械で `warifuri secretary enable` を実行します。`claude` が PATH にないときは、そう伝えて何も書かずに終わります。あれば、デバイス `secretary` のシークレットを発行し(前に発行したものがまだ使えれば、そのまま使います)、データのフォルダの `secretary/mcp.json` に、このサーバーの URL とシークレットを入れた MCP の設定を、本人だけが読める形で書きます。シークレットはこのファイルにだけ置き、コマンドの引数にも、環境変数にも、画面やログにも出しません。設定ファイルをなくしたときは、もう一度 `enable` を実行すると、古いシークレットを取り消して新しく発行します。最後に `warifuri.env` に `WARIFURI_SECRETARY=on` を書き、本人が自分ですること(その機械で一度 `claude` にログインする、`warifuri serve` を動かし直す)を出します。`warifuri secretary disable` は `WARIFURI_SECRETARY=off` を書き、`secretary` のシークレットを取り消します。

`plugins.yaml` には書きません。`plugins.yaml` に秘書の行があると、エージェントの気づきが受信箱に入るようになりますが(プロフィールの節)、受信箱からナレッジへ移すツールがまだないためです。受信箱を使うかどうかは、使う人が `plugins.yaml` で決めます。

#### 時計

`warifuri serve` は、`WARIFURI_SECRETARY=on` で、`claude` が PATH にあり、`secretary/mcp.json` があるときだけ、小さな時計を動かします。cron やタスク スケジューラを用意する必要はありません。30秒ごとに時刻を見て、時刻が来た仕事を起こします。時刻はサーバーの機械の時刻で、既定は次のとおりです。どれも設定で変えられます([設定](configuration.md))。

| 仕事 | 既定の時刻 | 設定 |
|---|---|---|
| 毎晩の見張りと組み直し(`nightly`) | 毎日 23:00 | `WARIFURI_SECRETARY_NIGHTLY` |
| 朝の報告(`morning`) | 毎日 07:00 | `WARIFURI_SECRETARY_MORNING` |
| 受信箱の整理(`inbox`) | 日曜 23:00 | `WARIFURI_SECRETARY_INBOX` |

夜の時間帯は既定で 23:00〜07:00 です(`WARIFURI_SECRETARY_NIGHT`)。秘書はこのあいだ人を呼び出さず、報告に書きます(原則17)。いまの秘書には人を呼び出す道具がないので、どの時間帯でも、知らせることは報告に書きます。

仕事は一度に1つだけ動かします。同じ時刻に来た仕事は、毎晩、朝、受信箱の順に、前の仕事が終わってから動かします。日曜の受信箱の整理は、同じ 23:00 の毎晩の仕事のあとに動きます。前の時刻に起こした仕事がまだ終わっていないうちに次の時刻が来たら、その仕事は飛ばし、1行だけ記録に出します。`warifuri secretary run` で手で動かしている仕事とも重ならないよう、動いているあいだは `secretary/run.lock` にその process の番号を置きます。

止まっていたあいだの仕事は、取り戻しません。時計が数えるのは、`serve` が動き出したあとの時刻だけです。機械が眠っていて時刻を見るのが遅れたときは、仕事ごとに、遅れた時刻のうちいちばん新しい1回だけを動かし、それも1時間を超えて遅れていれば動かさずに、1行記録に出します。朝に起きた機械が、ゆうべの見張りと朝の報告を立て続けに動かすことはなく、朝の報告だけが時刻どおりに動きます。

1回の仕事は既定で20分まで(`WARIFURI_SECRETARY_TIMEOUT`)で、超えたら止めます。`serve` を止めたときも、動いている仕事を止めます。`serve` の画面に出すのは、仕事の始まりと終わり、終わったときの終了コードと、飛ばした理由だけです。`claude` の出力にはデータベースの中身が入るので、データのフォルダの `secretary/logs/<仕事>.log` に、本人だけが読める形で書きます。1つ前の回の分は `<仕事>.prev.log` として残します。

#### 秘書が使えるもの

`claude` は次の形で起こします。手引きは標準入力で渡すので、Windows のコマンドの長さの上限にかかりません。

```
claude -p --mcp-config <データのフォルダ>/secretary/mcp.json --strict-mcp-config \
       --allowedTools mcp__warifuri --disallowedTools Bash,Edit,Write,Read,WebFetch,…
```

Claude Code は、MCP サーバーのツールを `mcp__<サーバーの名前>__<ツールの名前>` と呼びます(`mcp__warifuri__board` など)。`--allowedTools mcp__warifuri` は、そのサーバーのツールをすべて許します(`mcp__warifuri__*` と同じです)。コマンド、ファイルの読み書き、Web の組み込みのツールは `--disallowedTools` で断ります。`--strict-mcp-config` を付けるので、その機械の `claude` に登録したほかの MCP サーバーは読み込みません。`warifuri connect` でこの機械を本人のデバイスとしてつないでいても、秘書はデバイス `secretary` として書き、記録にもそう残ります。

`claude` は Claude のアカウントでログインしているので、そのままでは claude.ai に足したコネクタ(Gmail、Google カレンダー、Notion など)も一緒に読み込みます。秘書が warifuri の決まりの外でメールを送ったり、本人のカレンダーを書き換えたりしないよう、既定では `ENABLE_CLAUDEAI_MCP_SERVERS=false` を付けて起こします。warifuri の設定の値(`WARIFURI_` で始まる環境変数)も、`claude` には渡しません。

カレンダーを秘書に渡すかどうかは、本人が考えて決めます。渡すときは、`WARIFURI_SECRETARY_CALENDAR_TOOLS` にカレンダーの MCP のツールを書きます(`mcp__calendar` のような形、カンマ区切り)。書くと `--strict-mcp-config` を外して、その機械の `claude` に登録した MCP サーバーも読み込み、`--allowedTools` にそのツールを足します。claude.ai のコネクタのカレンダーを渡すときは、あわせて `WARIFURI_SECRETARY_CONNECTORS=on` にします。どちらの場合も、使えるのは書いたツールだけで、ほかのツールは `claude -p` が断ります。カレンダーの読み書きは、上の「カレンダー」の小節の決まりに従います。

#### 手引き

仕事ごとの手引きは、パッケージの `harness/secretary/` にある Markdown です。`common.md`(どの仕事にも共通の決まりと報告の書き方)と、仕事ごとの `nightly.md`、`morning.md`、`inbox.md` をつなぎ、頭にいまの日時、夜の時間帯、カレンダーがあるかを付けて渡します。

- 毎晩の見張りと組み直し: `settings`、`autonomy`、`board`、`schedule` で状況をつかみ、期日のあるゴールごとに、残りのタスクの見積りと `free_time` の空き時間を比べます(原則12)。順序のないタスクが並んでいれば、順序の案を出します(原則3)。過ぎた予定や取れなくなった予定は、`free_time` と `book` で上限の中に置き直します。`stale` と記録から閉じ忘れを探します。
- 朝の報告: 夜のあいだに変わったこと、今日決めてほしいこと、今日の予定の3つだけを短く書きます。前に出した案は、状況が悪くなったときだけ言い直します(原則13)。
- 受信箱の整理: プロフィールごとに `context` で受信箱といまのナレッジを読み、入れる、重なる、古い、確かめが要る、領域の外、要らない、に分けます。受信箱から消すツールとナレッジを書き換えるツールがまだないので、いまは案を書くだけです。

どの仕事でも、秘書は最初に `autonomy` を読み、「やってから知らせる」の種類だけを自分で行い、「聞いてから」の種類は報告に案として書きます(原則13)。人が主導するゴールでは案だけにします(原則8)。期日は作らず、上限は書きません。本人の答えはこの場にないので、`autonomy_outcome` は呼びません。本人が報告の案に答えた会話で、そこにいるエージェント(軽い秘書など)が記録します。結果は `report` で報告として書き、書くことのない日は書きません。

秘書が閉じ忘れの証拠にするのは、データベースの記録(着手、`next`、変更)だけです。秘書はサーバーの機械にいるので、使う機械の中のファイルは見ません。

### 軽い秘書(スキル)

秘書のプラグインとは別に、warifuri は軽い秘書をスキルとして配ります。パッケージの `harness/skills/warifuri-secretary/` にあり、`warifuri connect` が、ほかのスキルと一緒にハーネスのスキルのフォルダへ写します。中身は Markdown の指示書だけで、MCP のツールしか使わないので、Claude Code でも Codex でも同じように動きます。

軽い秘書は、人が話しかけたときに、いま使っているハーネスの中で動きます。常駐も定時の仕事もしません。できるのは、`board` を読んで今日の候補をゴールごとに並べること、`stale` の候補を1件ずつ本人に聞いて閉じる・先送り・再開・分けるのどれかにすること、`flow` とタスクの `next` から次の一手をすすめて `start` すること、本人の言った人や決まりを `note` でナレッジに入れることです。ハーネスにカレンダーの MCP がつながっていれば、予定を組む前に今週の予定を取り込み、取った時間をカレンダーにも書くかを聞きます(上のカレンダーの小節)。どの書き込みも、本人の了承を得てからにします。期日は作らず、時刻も決めません。

秘書のプラグインとの違いは、だれが起こすかと、秘書の自律度(原則13)を持つかです。軽い秘書は呼ばれたときだけ動き、自律度を上げないので、どの動きも毎回「聞いてから」です。秘書のプラグインはサーバーの機械で決まった時刻に動き、毎晩の見張りと報告、スケジュールの組み直し、受信箱の整理をして、了承が続いた種類は、やってから知らせるようになります。軽い秘書の記録は、それを呼んだ使う機械のデバイスとして残ります。秘書のプラグインの報告にある案に本人が答えたときは、軽い秘書がその答えを `autonomy_outcome` で記録します。

### プラグインの形

warifuri が用意するプラグインも、使う人が自分で書くプラグインも、同じ形にします。プラグインが出せるものは次の4つです。

| 出せるもの | 例 |
|---|---|
| MCP のツール | 監視の `server_status`、作業用ブラウザの `browse` |
| 定時の仕事 | 毎晩の組み直し、10分おきの見張り |
| 秘書への説明 | そのプラグインのツールをいつどう使うか。秘書の指示書に足される短い文 |
| 設定の形 | そのプラグインが読む設定の項目と、既定値 |

プラグインがデータベースやプロフィールや設定に触れるのは、核のツールと API からだけです。期日や完了の条件の決まりは、プラグインからも外せません。ほかのプラグインを使うときも、直接は呼ばず、MCP サーバーに出ているツールを通します。

プラグインはどこに置いてもかまいません。warifuri の `plugins/` の中、手元のフォルダ、npm のパッケージのどれでも、`plugins.yaml` に書けば読み込みます。プラグインは使う人が信じて入れるコードなので、足すツール、外への通信、定時の仕事を説明の欄に書かせ、入れるときに使う人へ見せます。

### バニラと個人の拡張

```
warifuri(公開。手を入れずにそのまま使える)
   ▲ 依存する(写して改造はしない)
個人のプラグイン(使う人の手元。要る人だけ)
   └─ 自分の環境に合わせた機械など
```

warifuri は、設定を書くだけで動くようにします。自分の環境に合わせたいことは、warifuri を写して改造せず、設定と個人のプラグインで行います。こうしておけば、warifuri を新しい版にしても個人の部分はそのまま残ります。

個人のプラグインのうちほかの人にも使えそうなものは、固有の語を設定へ出してから warifuri に戻します。核を変えないとできないことは、個人の側で抱えず、warifuri への変更として出します。

## プロフィール

プロフィールは、サーバーの設定フォルダの `profiles/` の中に、1つずつフォルダを持ちます。プロフィールの名前(研究、仕事など)は使う人が付け、フォルダの名前はそこから決まります。

```
profiles/
  研究/
    profile.yaml     既定(人が主導か、スケジュールの色、stale の日数)
    people.md        この領域の人
    knowledge.md     決まりと事実
    knowledge/       ナレッジが長くなったときに話題ごとに分けたもの
    procedures/      手順。1つの手順につき1ファイル
    inbox.md         受信箱。エージェントの気づきを、秘書が整理するまで置く
```

knowledge.md がおよそ200行を超えたら、話題ごとに `knowledge/` に分けます。秘書がいれば秘書が週1回の整理のときに分け、いなければ人が分けます。プロフィールが1つの人は、フォルダも1つです。最初は people.md と knowledge.md だけでも動きます。

### フォルダの名前

プロフィールの名前は自由に付けられるので、そのままでは Windows や Mac のフォルダの名前にできないことがあります。そこで、名前を NFC にそろえたうえで、フォルダの名前に使えない文字(`< > : " / \ | ? *`、制御文字)と `%` を、UTF-8 のバイトごとに `%XX` と書きます。先頭と末尾の `.` と空白、Windows が予約している名前(`CON`、`NUL`、`COM1` など)の最初の1文字も同じように書きます。ほかの文字はそのまま残すので、日本語の名前はそのまま読めます。`%` はいつも書き換えるので、別の名前が同じフォルダになることはありません。ただし、大文字と小文字だけが違う名前は、それを区別しない Mac や Windows のディスクでは同じフォルダになります。フォルダの名前は 255 バイトまでで、超える名前は断ります。

### ナレッジの読み書き

`context` は、people.md と knowledge.md の本文と、`knowledge/` と `procedures/` のファイル名(`procedures/提出.md` の形)を返します。本文は1つのファイルにつき 64 KiB まで返し、超えた分は切って `truncated` を付けます。ファイル名は1つのフォルダにつき 200 個までです。`name` で取りにいけるのは、この一覧に出る名前だけです。渡された道をそのまま開くことはしないので、`..` などでプロフィールの外は読めません。隠しファイルと、リンクになっているファイルは一覧に出しません。

`note` は書き足すだけで、すでに書かれている行は変えません。1回に 4000 文字まで書けます。1件は1つの箇条で、`- 2026-10-24 「本人の言葉」 本文 (デバイス)` の形になります。「未確認」も同じ位置に付き、受信箱には印を付けません。`close` から入ったものには、デバイスの後ろにタスクの id が付きます。日付はサーバーの機械の日付です。プロフィールのフォルダがなければ、最初の `note` で作ります。

書いたことは、データベースの記録にも、プロフィールの名前を id にして残します(種類は `knowledge`)。1000 文字までは本文ごと、それより長いものは最初の 200 文字と長さとハッシュだけを残します。

秘書を入れているかどうかは、データのフォルダの `plugins.yaml` に `secretary` の行があるかで見分けます。`note` のたびに読むので、入れたあとにサーバーを動かし直す必要はありません。

## 使う人が書く設定

この節のうち、`warifuri.env`、`profiles/`、`secrets.env` のほかのファイル(`principles.md`、`habits.yaml`、`plugins.yaml`)は、v0.1 では未実装の設計です。`plugins.yaml` だけは、`note` が秘書を入れているかを見分けるために読みます(上の節)。

サーバーの設定フォルダに置きます。書くのは、人か、`profile` のツールを使う秘書です。生活、場所と移動時間、上限の3つは、ファイルではなくデータベースに持ちます(下の小節)。

| ファイル | 中身 |
|---|---|
| `warifuri.env` | サーバーの機械に固有の値(上の節) |
| `principles.md` | 原則の書き換え。秘書とエージェントへの指示として配られる |
| `profiles/` | プロフィール(上の節) |
| `habits.yaml` | 最初に入れる繰り返しの予定。データベースの習慣の表に入り、あとは `habit` のツールで直す |
| `plugins.yaml` | 入れるプラグイン |
| `secrets.env` | 秘密(GitHub の OAuth App の Secret など)。本人だけが読めるようにする |

名前、ドメイン、プロフィールの名前は設定から読み、コードには書きません。作業フォルダのパスは、データベースの作業フォルダの表に持ちます。秘書を入れた場合は、最初の会話で秘書が生活と場所(`settings` のツール)、`profiles/`、habits.yaml を一緒に作ります。設定のひな形は、架空の人の例として `examples/` に置き、写して書き換えれば動く形にします。

### 生活、場所、上限

スケジュールを組むときに読む本人の設定は、生活(`life`)、場所と移動時間(`places`)、上限(`limits`)の3つです。どれもデータベースの `settings` の表に、区分と項目の名前をつないだキー(`life.rules`、`limits.day_max_hours` など)で、値を JSON にして持ちます。Web 画面のプロフィールが `profile.name` などで入っているのと同じ表です。変えたことは記録に残り、種類は `settings`、id は区分の名前です。読み書きは `settings` のツールで行い、何も渡さなければ3つを読むだけです。書いていない項目は既定値で返し、どの項目が既定値のままかを `defaults` に並べます。区分に null を渡すと、その区分は既定値に戻ります。

| 区分 | 形 | 既定値 |
|---|---|---|
| `life` | `rules`: 生活の決まりを1行ずつ書いた文字列の配列(50件まで、1件200文字まで)。寝る時間、食事、決まった用事などを、ふつうの言葉で書く | 空 |
| `places` | `places`: 本人が行く場所の `{ name, note }` の配列(50件まで)。`travel`: 2つの場所のあいだの移動時間の `{ from, to, minutes }` の配列。片道を1回書けば、帰りも同じとみなす | 空 |
| `limits` | `day_max_hours`(1日に予定を置く時間の上限、0.25 きざみで 24 まで)、`block_min_minutes` と `block_max_minutes`(1つの予定の長さ、5〜1440 分)、`earliest` と `latest`(予定を置いてよい時刻、`HH:MM`、`latest` は `24:00` まで) | 8 時間、30〜120 分、09:00〜21:00 |

`life` と `places` は、渡した形にまるごと置き換えます。`places` で場所だけを渡したときは、残った場所どうしの移動時間を残します。`limits` は、渡した項目だけを変え、null の項目は既定値に戻します。変えたあとの値が、`earliest` が `latest` より前で、そのあいだが `block_min_minutes` 以上で、`block_min_minutes` が `block_max_minutes` 以下になっていなければ断ります。ここの `places` は、本人が実際に行く場所のことで、作業フォルダ(`place` と `places` のツール)とは別のものです。

`life` と `places` は、エージェントも秘書も書けます。上限を変えるのは本人だけです(原則14)。そのため、`limits` を書くときは、本人がその会話で決めたことを `by_person: true` で示します。付けなければ断り、本人に提案して了承を得るよう返します。人が決めて書いた上限は、記録の動作が `decide` になります。この印は呼び出す側の申告で、warifuri からは人と AI を見分けられません。誤って書かれた上限は、記録から見つけて戻せます。`free_time` は、この上限の中で空き時間を探します。
