# 連携の例

## Google カレンダー

秘書が Google カレンダーを読み、決めた予定をカレンダーに書き出せるようにします。warifuri は Google に自分ではつながりません。秘書を動かしている Claude Code の、Google カレンダーのコネクタを使います。

### 1. コネクタの用意

サーバーの PC で秘書が使っている Claude のアカウントに、claude.ai で Google カレンダーのコネクタを追加します。予定を見たい Google のアカウントでつなぎます。

### 2. 秘書への受け渡し

サーバーの PC の `warifuri.env` に次の2行を書き、サーバーを起動し直します。

```
WARIFURI_SECRETARY_TOOLS=mcp__claude_ai_Google_Calendar=own
WARIFURI_SECRETARY_CONNECTORS=on
```

`own` は「warifuri が作ったものだけ書く」範囲です。秘書はカレンダーを読み、自分が入れた予定だけを書き出します。ユーザーが入れた予定は書き換えません。

#### 書き出す先

秘書が書く予定は、すべてユーザーのメインのカレンダー(Google アカウントの名前のカレンダー)に入ります。タスクのために取った時間、ユーザーに頼まれた予定、移動の時間も同じです。warifuri 用のカレンダーは作らず、ほかのカレンダーにも書きません。カレンダーが分かれると、どの予定がどこにあるか分からなくなり、重なりも見落としやすくなるためです。Google カレンダーを見れば、warifuri の予定も全部分かるようにします。

秘書が作った予定は、説明の最後の行に「warifuri で作成」と入ります。warifuri は、この文ではなく、予定ごとに覚えている組(`source` と `external_id`)で自分の予定を見分けます。説明にこの文があっても、組がない予定はユーザーの予定として扱います。

曜日ごとの居場所(研究室にいる時間など、設定の `week`)は、Google カレンダーには入れません。warifuri の画面とカレンダーの画像に、帯で出るだけです。

前に秘書が別のカレンダーに予定を書いていたときは、秘書が、何件をどのカレンダーからメインのカレンダーへ移すかを聞きます。了承すると、メインのカレンダーに作り直し、前のカレンダーの予定を消します。消した予定は、Google カレンダーのごみ箱から戻せます。過ぎた予定と、前のカレンダーそのものは残るので、要らなければ自分で消します。

秘書は1時間ごとに(夜を除く)、カレンダーの予定を warifuri に取り込みます。カレンダーで消した予定は、warifuri からも消えます。もっと早く取り込みたいときは、下の「カレンダーの変更をすぐに取り込む」の設定をします。

### 3. 動作の確認

秘書の画面で「明日の予定を教えて」と話しかけ、カレンダーの予定が返ってくれば完了です。

<details>
<summary>複数の Google アカウントを使っている場合</summary>

仕事や就活など、ほかのアカウントのカレンダーも見せたいときは、それぞれのアカウントの Google カレンダーで、メインのアカウントにカレンダーを共有します。共有の権限は「予定の詳細をすべて表示」にします。空き時間だけの共有では、秘書が予定の中身から判断できません。

メインのアカウントから見えるカレンダーは、秘書がまとめて読みます。予定をアカウントのあいだでコピーすることはしません。

</details>

<details>
<summary>エージェントのアカウントが、カレンダーのアカウントと違う場合</summary>

Codex を会社のアカウントでログインしているときなど、エージェントのコネクタで触るカレンダーが、ユーザーのカレンダーと違うことがあります。そのエージェントにはカレンダーのコネクタを使わせず、予定は warifuri を通すようにします。エージェントを使う PC の `warifuri.env` に書きます。

```
WARIFURI_CALENDAR_CODEX=gcp
```

Claude Code なら `WARIFURI_CALENDAR_CLAUDE=gcp` です。書いたあとに `warifuri connect` を実行し直すと、そのエージェントがカレンダーのツールを使おうとしたとき、止めて warifuri を使うよう伝えるようになります。

</details>

### カレンダーの変更をすぐに取り込む

Google Cloud の設定がなくても、カレンダーは使えます。既定では秘書が1時間ごとに同期します。Google Cloud の OAuth クライアントを用意して warifuri に渡すと、warifuri が AI を使わずにカレンダーを読み、変更を1分以内に取り込みます。

warifuri が Google に求めるのは、カレンダーを読む許可だけです。カレンダーに書くのは、これまでどおり秘書のコネクタです。

OAuth クライアントは、warifuri を置いている人(運営者)本人だけが使います。warifuri は共有の OAuth クライアントを配っていないので、運営者がそれぞれ自分の Google Cloud プロジェクトとクライアントを作ります。ほかの人のアカウントでのログインには使いません。

#### 1. Google Cloud の用意

1. [Google Cloud コンソール](https://console.cloud.google.com/)で自分のプロジェクトを作り、「API とサービス」のライブラリで Google Calendar API を有効にします。
2. 「OAuth 同意画面」(Google Auth Platform)を作ります。ユーザーの種類は「外部」にします。
3. 「ブランディング」のページに、自分のドメインで次の3つを書きます。ページは warifuri のサーバーが出します(下の「公開のページ」)。
   - アプリのホームページ: `https://<自分のドメイン>/about`(例: `https://warifuri.example.com/about`)
   - プライバシーポリシー: `https://<自分のドメイン>/privacy`
   - 承認済みドメイン: 自分のドメイン(例: `example.com`)
4. 「対象」のページで、公開ステータスを「本番環境」にします。「テスト」のままだと、許可が7日で切れて、ログインし直すことになります。本番環境にするのは7日で切れないようにするためで、ほかの人に使わせるためではありません。Google の確認(検証)の申請はしません。確認の画面や「確認が必要」の表示が出ても、自分だけで使うなら確認なしで使えます。ログインのときに「このアプリは Google で確認されていません」の警告が出て、使える人数は100人までになりますが、運営者1人なので困りません。
5. 「認証情報」(クライアント)で OAuth クライアント ID を作ります。アプリケーションの種類は「デスクトップ アプリ」にします。クライアント ID とクライアント シークレットをコピーします。

<details>
<summary>公開のページ(/about と /privacy)</summary>

`warifuri serve` は、ログインもデバイスの鍵もなしで、次の2つのページを出します。

- `/about`: warifuri の説明と、GitHub のリポジトリへのリンク
- `/privacy`: プライバシーポリシー。カレンダーから読むもの、データの扱い、許可の取り消し方、問い合わせ先

問い合わせ先は、`warifuri.env` の `WARIFURI_OPERATOR_CONTACT` にメールアドレスか URL を書くと載ります。書かなければ「このサーバーの運営者」と出ます。

```
WARIFURI_OPERATOR_CONTACT=https://example.com/contact
```

Cloudflare Tunnel と Cloudflare Access のように、サーバーの前段でログインを求めているときは、`/about` と `/privacy` の2つの道だけログインなしで通します。Google はこの2つのページを、ログインなしで開けるかを見ます。

</details>

#### 2. warifuri への受け渡し

サーバーの PC の `warifuri.env` にクライアント ID を、`secrets.env` にクライアント シークレットを書きます。

```
# warifuri.env
WARIFURI_GOOGLE_CLIENT_ID=1234567890-example.apps.googleusercontent.com
```

```
# secrets.env
WARIFURI_GOOGLE_CLIENT_SECRET=...
```

サーバーの PC で次のコマンドを実行します。

```bash
warifuri google login
```

表示された URL をブラウザで開き、自分の Google アカウントで許可します。「このアプリは Google で確認されていません」と出たら、「詳細」から先に進みます。ブラウザがサーバーの PC と別の PC にあるときは、許可のあとに開けないページ(`http://127.0.0.1:…`)に移るので、そのページの URL をアドレスバーからコピーし、コマンドに貼り付けて Enter を押します。許可のトークンは `secrets.env` に入り、画面には出ません。

`warifuri.env` に `WARIFURI_GOOGLE_ACCOUNT=<自分の Google アカウントのメールアドレス>` を書いておくと、ほかのアカウントで許可したときにログインを断り、トークンを保存しません。

最後に `warifuri serve` を起動し直します。

#### 3. 動作の確認

起動のログに `calendar: watching Google Calendar every 1 min` が出ていれば、取り込みが始まっています。Google カレンダーで予定を動かし、1〜2分後に warifuri のカレンダーの画面で同じように動いていれば完了です。新しく作った予定だけは、作ってから2分たつまで取り込みません。秘書がカレンダーに書いた予定を、warifuri の予定と結びつけ終えるのを待つためです。

予定が増えた、動いた、消えたときは、秘書の会話に1行ずつ残り、秘書は次に話すときにそれを読みます。

<details>
<summary>変更のたびに秘書に見てもらう場合</summary>

`warifuri.env` に次の1行を足すと、予定が変わるたびに秘書が起き、タスクの予定と重なっていないか、その予定の前に終えるタスクがないかを見て、あれば聞いてきます。変更のたびに秘書が1回動くので、その分 Claude の利用枠を使います。夜の時間帯には起こしません。

```
WARIFURI_GOOGLE_CALENDAR_WAKE=on
```

</details>

<details>
<summary>数秒で取り込みたい場合</summary>

`warifuri.env` に次の1行を足すと、カレンダーが変わったときに Google から warifuri に知らせが届き、数秒で取り込みます。

```
WARIFURI_GOOGLE_CALENDAR_PUSH=on
```

`WARIFURI_PUBLIC_URL` が https で、Google から届く必要があります。知らせは `<WARIFURI_PUBLIC_URL>/api/google/calendar/notify` に届くので、トンネルや逆プロキシでログインを求めているときは、この道だけログインなしで通します。warifuri は、自分が開いたチャンネルの合言葉が付いた知らせだけを受け取ります。

知らせを受け取れないカレンダーは、起動のログに `calendar: no push for one calendar` と出て、1分ごとの確認で取り込みます。

</details>

<details>
<summary>取り込みの間隔を変える、同期の仕事を減らす場合</summary>

カレンダーに変更がないかを聞く間隔は、`WARIFURI_GOOGLE_CALENDAR_POLL` に分で書きます(既定は 1)。

warifuri が自分で取り込んでいるあいだ、秘書の同期の仕事は取り込みをせず、カレンダーへの書き出しだけをします。回数を減らすときは `WARIFURI_SECRETARY_SYNC=every 6h` のように、止めるときは `off` と書きます。

</details>

## Discord

秘書の質問、朝の報告、秘書の失敗を、Discord のチャンネルに送ります。朝の報告には、1週間のカレンダーの画像も付きます(サーバーの PC に `rsvg-convert` が要ります。Debian や Ubuntu なら `librsvg2-bin`)。秘書の画面を開いていなくても、判断が要ることに気づけます。夜の時間帯に起きたことは、夜が明けてからまとめて送ります。

設定で有効にすると、Discord で秘書と話せます。チャンネルに書いたことは秘書の会話に入り、秘書の返事が Discord に届きます。秘書の質問の選択肢と返事の候補はボタンになり、押すとその場で答えられます。秘書の質問に問いが2つ以上あるときは、問いごとに番号を付けて1通ずつ届きます。返事の「スレッドで話す」を押すか、秘書の画面でスレッドを開いて話すと Discord のスレッドが開き、そこに書いたことは秘書の画面の同じスレッドに入って、返事もそのスレッドに届きます。同じやり取りは秘書の画面にも残ります。秘書の画面で書いたことには「(Web から)」を、エージェントからの依頼には「(エージェントから)」を付けて Discord にも送り、その返事も Discord に届くので、Discord を見れば会話をひと続きで追えます。

### 1. ボットとチャンネルの用意

Discord の Developer Portal でアプリとボットを作り、ボットのトークンをコピーします。ボットを自分のサーバーに招き、自分だけが見るチャンネルで「メッセージを送信」できるようにします。Discord で話すときは、同じチャンネルで「公開スレッドの作成」と「スレッドでメッセージを送信」もできるようにします。Discord の設定で開発者モードをオンにし、チャンネルと自分のユーザーを右クリックして、それぞれの id をコピーします。

### 2. warifuri への受け渡し

トークンは秘密なので、サーバーの PC にユーザーだけが読めるファイルで置きます(中身はトークンだけか、`DISCORD_BOT_TOKEN=` の1行)。サーバーの PC の `warifuri.env` に次の3行を書き、サーバーを起動し直します。

```
WARIFURI_DISCORD_TOKEN_FILE=~/.config/warifuri/discord.env
WARIFURI_DISCORD_CHANNEL=123456789012345678
WARIFURI_DISCORD_USER=234567890123456789
```

`WARIFURI_DISCORD_USER` を書くと、質問と失敗のときに自分にメンションします。メンションは、ほかの人には飛びません。

Discord で秘書と話すときは、次の1行も足します。チャンネルで秘書に渡すのは、`WARIFURI_DISCORD_USER` の人が書いたことだけです。同じボットで話すほかの仕組みが動いていると、両方が答えてしまうので、先に止めます。

```
WARIFURI_DISCORD_CHAT=on
```

Developer Portal で、ボットの「Message Content Intent」を有効にします。これがないと、書いたことの中身を読めません。

### 3. 動作の確認

サーバーの起動のログに `discord:` で始まる1行が出ていれば、送る準備ができています。秘書の画面で質問が出たとき、Discord のチャンネルにも同じ質問が届けば完了です。

Discord で話すときは、ログに `discord: connected` が出ていれば、受け取る準備ができています。チャンネルに何か書いて、秘書の返事が Discord に届けば完了です。スレッドは、返事に「スレッドで話す」が出たときに押して、開いたスレッドに書き、返事がそのスレッドに届くことで確かめます。

## GitHub

GitHub の PR と Issue の状態を、warifuri にコピーします。タスクに書いた PR がマージされると、秘書が「終わっていそうなタスク」として確かめに来ます。レビューを頼まれた PR や、担当になった Issue も、秘書が読めます。

warifuri は GitHub の Webhook で変化を受け取るだけで、GitHub には書き込みません。サーバーが GitHub から届く URL(`WARIFURI_PUBLIC_URL`)で動いている必要があります。

### 1. Secret の用意

Webhook の Secret にする文字列を作ります。

```bash
openssl rand -hex 32
```

サーバーの PC の `secrets.env` に書き、サーバーを起動し直します。

```
WARIFURI_GITHUB_WEBHOOK_SECRET=<作った文字列>
```

起動のログに `GitHub webhook on` の1行が出ます。

### 2. Webhook の作成

組織のリポジトリをまとめて受け取るときは、組織の Settings の Webhooks で作ります。個人のアカウントには、アカウント全体の Webhook がないので、リポジトリごとに Settings の Webhooks で作ります。どちらも、次のように入力します。

| 項目 | 値 |
|---|---|
| Payload URL | `<公開の URL>/api/github/webhook` |
| Content type | `application/json` |
| Secret | 手順1の文字列 |
| SSL verification | Enable |
| events | 「Let me select individual events」で Pull requests と Issues |

作ると GitHub が `ping` を送ります。Webhook の Recent Deliveries で、応答が 200 になっていれば届いています。

### 3. 読み込むオーナーの指定

はじめは、どのオーナー(ユーザーか組織)も読み込みません。読み込むオーナーは、秘書に「example-org の PR を読み込んで」と頼むか、Web 画面のナレッジの「GitHub」で追加します。オーナーごとに「読み込む」「読み込まない」を選べて、変えた設定は次に届く知らせから効きます。

「一覧にないオーナー」を「読み込む」にすると、Webhook を付けたオーナーをすべて読み込みます。その場合も、「読み込まない」にしたオーナーは読み込みません。読み込まないオーナーの知らせは、届いても保存しません。

### 4. タスクとの結びつけ

タスクの本文、成果、次の一手のどれかに、PR を `example-org/widgets#12` か URL で書いておきます。その PR がマージされると、開いたままのタスクが `stale` の `merged` に出て、秘書が毎晩と週の完了確認で根拠にします。

## Gmail と Notion

秘書に、メールや Notion のページを読ませます。メールから予定や締切に気づいたり、調べものの資料にしたりできます。カレンダーと同じく、サーバーの PC で秘書が使っている Claude のアカウントにコネクタを追加し、`warifuri.env` の `WARIFURI_SECRETARY_TOOLS` に足します。

```
WARIFURI_SECRETARY_TOOLS=mcp__claude_ai_Google_Calendar=own,mcp__claude_ai_Gmail=read,mcp__claude_ai_Notion=read
```

`read` は「読むだけ」の範囲です。メールを送る、下書きを作る、ページを直すといった書くツールは、秘書が使おうとしても止まります。メールを送らせたいときは `write` にします。`write` でも、外に出す前には毎回ユーザーに聞きます。

## Muse(外の AI エージェント)

Muse のような、ほかの会社のクラウドで動く AI エージェントに、warifuri の予定とタスクを読ませて、提案をさせます。その AI に渡した中身は、その会社のクラウドに残ります。そのため、見せる範囲を絞ったシークレット(範囲つきのシークレット)でつなぎます。

### 見せる範囲

範囲つきのシークレットでは、プロフィールごとに、人・ナレッジ・タスクの中身を伏せられます。下の表の「伏せたプロフィール」は、`--hide` で選んだプロフィールです。

| もの | 見せるもの | 伏せたプロフィールで見せないもの |
|---|---|---|
| 予定 | 題、時間、場所 | 場所。予定のメモと作成者は、どのプロフィールでも見せない |
| ゴールとタスク | すべての項目 | 題・期限・状態・ゴール以外(説明、次の一手、成果、完了の条件、ゴールのあるべき姿、記録、だれが着手しているか) |
| 人 | 人の一覧とメモ | 人とメモのすべて。一覧、検索、id の指定のどれでも断る |
| ナレッジ | knowledge.md、knowledge/、procedures/、受信箱 | すべて |

書き込みは、ナレッジや人へのメモ(`note`)、秘書への依頼(`ask_secretary`)、タスクへの下調べ(`prep`)だけです。伏せたものがあるプロフィールには、メモを書けません。タスクの中身を伏せたプロフィールのタスクには、下調べを書けません。タスクを作る・閉じる、予定を入れるといった、ほかの書き込みのツールは、ツールの一覧にも出ません。作業フォルダの一覧、秘書の報告と提案、動きの記録、設定、GitHub のコピーも読めません。フックが使う `/api` は断ります。

### 1. シークレットの作成

サーバーの機械で、範囲つきのシークレットを作ります。次の例は、プロフィール「仕事」の人・ナレッジ・タスクの中身を伏せます。

```bash
warifuri key add muse --guest --hide 仕事
```

範囲は、次のフラグで変えられます。

| フラグ | 意味 | 例 |
|---|---|---|
| `--guest` | 範囲つきにする(すべてのプロフィールを見せ、書き込みは `note`、`ask_secretary`、`prep`) | `--guest` |
| `--hide <プロフィール>` | そのプロフィールの人・ナレッジ・タスクの中身を伏せる。`=` の後に、伏せるものだけを書ける(`people`、`knowledge`、`details`) | `--hide 仕事`、`--hide 仕事=people,knowledge` |
| `--profiles <一覧>` | 見せるプロフィールを、これだけにする | `--profiles 趣味,研究` |
| `--write <一覧>` | 許す書き込み。空にすると読むだけになる | `--write note,prep`、`--write ""` |

作ったあとは、`warifuri key scope muse` で範囲を確かめ、同じフラグを付けて直します。シークレットを取り消すときは、`warifuri key revoke muse` を使います。

### 2. Muse への登録

Muse のチャットで、MCP サーバーの追加を頼みます。

```
warifuri という MCP サーバーを追加して。URL は https://app.example.com/mcp、方式は Streamable HTTP、認証は Authorization ヘッダーの Bearer トークン。
```

URL は、warifuri サーバーの公開の URL の後ろに `/mcp` を付けたものです。シークレットは、Muse が出すトークンの入力画面に貼ります。チャットの本文には貼りません。会話の記録に残るためです。

### 3. 動作の確認

Muse に「今週の予定と、締切の近いタスクを教えて」と頼み、予定とタスクの題が返ってくれば、つながっています。あわせて、伏せたプロフィールのタスクの説明が出ないことと、「仕事の人を教えて」が断られることを確かめます。

### 4. 下調べ

やりたいことをタスクに入れておくと、Muse が、人がまだ着手していないタスクを裏で下調べし、結果をタスクに書き戻します。人やエージェントがそのタスクに着手すると、その結果が出ます。

- Muse は `prep_candidates` で候補を読みます。既定で5件、点(`score`)の高い順で、それぞれに点の理由(`why`)が付きます。
- 点の材料は、本人の「下調べを頼む」の印、ほかのタスクを待たせている数、期限の近さ、本人が手を動かすタスクで調べものがありそうか、ゴールの期限、下調べがまだないか、です。二度手間や的外れの評価が多いゴールとプロフィールは点が下がります。重みは `src/ledger/ledger.mjs` の `PREP_SCORE` にまとめてあります。
- だれかが着手しているタスクは出ません。3日以内に下調べを書いたものと、2日以内に人か手元のエージェントが手を付けたもの(`recently_touched`)は、後ろに回ります。手を付けたものでも、下調べを頼まれていれば前に置きます。秘書と外の AI の書き込みと、印を付けただけのものは、手を付けたうちに入りません。
- 候補には、もう分かっていること(`known`)が付きます。説明の冒頭、次の一手、完了の条件、待っているもの、最近の記録の要点、前の下調べとその評価、最後に動いた日時とだれか、です。Muse には、調べる前にこれと `get` の記録を読ませ、分かっていることは調べ直さず、足りないところだけを調べさせます。
- 1日に書く数の目安は `WARIFURI_PREP_DAILY`(既定8件)です。返事の `today` に今日書いた数と残りが、`suggest` に今回の目安の件数が入ります。目安に届くと「今日はここまでです」と返します。断りはしません。
- 結果は `prep` で書きます。形は、結果の要約(`summary`)、成果物の置き場所(`artifacts`)、まだ分からないこと(`unknowns`)の3つです。続けるなら、次の一手(`next`)も書きます。
- 下調べを書いても、タスクの状態は変わりません。閉じるのは本人です。Muse には `close` を出していません。
- 書いた下調べは、`get` と、Web 画面のタスクの詳細の「下調べ」に出ます。秘書は朝のまとめで、下調べが付いたタスクを1行で知らせます。

#### 調べてほしいタスクに印を付ける

本人が「これを調べておいて」と思ったタスクには、「下調べを頼む」の印を付けます。印のあるタスクは候補の先頭に出ます。付け方は3つです。

- Web 画面のタスクの詳細で「下調べを頼む」を押す。外すときは「頼むのをやめる」。
- 秘書に「これ調べておいて」と言う。秘書が印を付けます。
- エージェントが `update` で `prep_wanted: true` を渡す。外すときは `false`。

Muse は印を付け外しできません。印を付けたあとに下調べが書かれると、その分の点は付かなくなります。

#### 下調べを評価する

下調べが役に立ったかどうかは、主に手元のエージェントが返します。

1. エージェントが `start` で着手すると、返事に「下調べがあります」の知らせと、いちばん新しい下調べが付きます。知らせには、使ったら評価を返すよう書いてあります。
2. エージェントは、読んで作業に使ったあと、`rate_prep` で評価を返します。下調べは `prep_id` か `task_id`(そのタスクのいちばん新しい下調べ)で指します。評価は `useful`(役に立った)、`duplicate`(二度手間。もう分かっていた)、`off`(的外れ)のどれかで、`null` で取り消します。`note` には、どこが使えたか、なぜ使えなかったかを1〜2行で書きます。
3. 評価を付けないまま `close` すると、返事の `prep_unrated` で評価を促します。閉じるのは止めません。

本人も、Web 画面の下調べの吹き出しにある「役に立った」「二度手間」「的外れ」で付けられます。もう一度押すと取り消します。だれが付けたか(エージェントのデバイスの名前か、本人の `web`)は下調べに残ります。

Muse は `prep_candidates` の返事の `feedback` で、30日分の評価の件数、付けた人ごとの件数、二度手間と的外れになった下調べの題と理由を読み、調べ方を直します。Muse は評価を付けられません。伏せたプロフィールの下調べの評価は、`feedback` にも出ません。

Muse には、たとえば次のように頼みます。

```
warifuri の prep_candidates を読んで、上から suggest の件数だけ、人がやらなくても進められる調べもの・技術検証・試作を進めて。
調べる前に、候補の known と get の記録を読んで、分かっていることは調べ直さないで。feedback で二度手間や的外れと言われた調べ方は避けて。
終わったら prep でタスクに書き戻して。形は、結果の要約、成果物の置き場所(URL かリポジトリのパス)、まだ分からないことの3つ。
タスクは閉じないで。閉じるかどうかは私が決める。「今日はここまで」と返ってきたら、その日は止めて。
```

前の版の `--guest` で作ったシークレットは、書き込みが `note` と `ask_secretary` のままです。下調べを書かせるには、範囲を付け直します。`key scope` は範囲をまるごと置き換えるので、`--hide` と `--profiles` も前と同じものを付けます。

```bash
warifuri key scope muse --hide 仕事 --write note,ask_secretary,prep
```

<details>
<summary>伏せる範囲の決め方</summary>

- ゴールとタスクの題は、伏せたプロフィールでも見えます。題に相手の名前や社名を書いているプロフィールは、`--profiles` で外します。
- 人の決まった列(名前、メール、電話、所属、役職、誕生日)は、その人が入っているどのプロフィールからも見えます。伏せたプロフィールの人が、見せるプロフィールにも入っていると、そちらから決まった列が見えます。
- 秘書への依頼の返事は、そのまま Muse に渡ります。依頼には、外の AI からの依頼であることと、伏せたプロフィールの中身を返事に書かないことを添えて秘書に渡します。この仕切りは秘書の判断に頼るので、伏せたい中身を秘書の会話で話すときは、気をつけます。

</details>
